# Verdict

**Bugs are innocent until reproduced.**

Verdict investigates flaky GitHub issues by experiment rather than by inference. You give it an issue, a maintainer-approved command, a bounded set of condition knobs and a run budget. It searches only that space, keeps every run record it produced and returns the smallest condition that met your reproduction threshold, a reviewable suspect range and a regression plan. When the evidence does not support a claim, it says so instead of rounding up to confidence. The only public write stays behind a maintainer's approval.

## What the demo shows and what it does not

The hosted case is a **conceptual fixture** built from [TrueForge issue #417](https://github.com/truefoundry/trueforge/issues/417). Every generated value is labelled as generated throughout the interface, and the workspace states plainly that execution status is `not run`.

This matters more than it sounds. A tool whose entire argument is "do not believe a claim without a record" cannot present modelled data as observation. Local setup, model registration and the read-only GitHub MCP path are verified. A complete live three-act investigation has not been recorded yet, so the workspace stays labelled rather than being dressed up as a real run.

## The three-act investigation

```text
GitHub issue
    |
    v
Hunter: find the trigger
    |
    v
Surgeon: localize the change
    |
    v
Insurance: keep it fixed
    |
    v
Maintainer review
```

**Hunter** searches only the approved condition space. Valid, partial and unresolved observations all stay on the board rather than being dropped for being inconvenient.

**Surgeon** narrows the reproduced condition to the smallest suspect range the evidence supports. A static inspection stays visibly distinct from a proven execution boundary.

**Insurance** turns the result into a regression plan and an exact publication manifest. In the demo this stays read-only.

## Evidence contract

Verdict separates exploration from proof:

1. Issue text and repository content start as untrusted input.
2. The investigation may use only approved commands, knobs and budgets.
3. Every accepted observation must match the evidence schema.
4. Deterministic reducers decide which claim the records support.
5. Missing or conflicting evidence produces an honest partial result.
6. A maintainer controls the only public write.

Points 3 and 4 are the ones that hold under pressure: because the reducers are pure and the schema is enforced, the same records always produce the same verdict, and a verdict cannot be talked into existence by the model that gathered the evidence.

## TrueForge agent harness

The sidecar in `apps/agent` targets TrueForge 0.1.x and keeps the three acts bounded:

- Dynamic subagents are configured for Hunter, Surgeon and Insurance
- Hugging Face Inference Providers supply the Qwen3.8-27B model route
- GitHub MCP access is restricted to four read tools and one approval-gated workflow trigger
- The remote MCP allowlist is requested explicitly, because GitHub excludes Actions tools from its defaults
- Sandbox file downloads are disabled and the host validates the exact workflow dispatch before approval

## Demo case: issue #417

The case studies a snapshot-registration request that may wait indefinitely when the upstream request never resolves. The workspace shows a 12-condition matrix with pinned, partial, unresolved and not-reproduced states, the exact proposed command for the selected condition, a static suspect range with its proof limitation visible, a regression plan and a read-only publication manifest.

Select different conditions and the evidence panel follows: outcome, signature match, duration, exit code, commit and run id.
